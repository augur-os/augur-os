# ADR-128: Contribution-Based Hub Assembly

## Context

The current plugin architecture (ADR-105) gives every skill its own `hub.id`, producing **40 standalone sidebar entries** from 14 bundles. Each hub ID creates a top-level page with its own layout, loading state, and navigation entry. This causes:

1. **Sidebar bloat** — 40 items overwhelm navigation. Users see `career`, `growth`, `content`, `linkedin-writer` as separate hubs when they belong together under "Career".
2. **No bundle-level overview** — Each bundle has no automatic summary page. Users must click into individual skill pages to see what's there.
3. **Duplicated boilerplate** — Every `augur.yaml` repeats hub title/subtitle/icon even when skills share a logical group.
4. **No widget composition** — Skills can't contribute summary widgets to a parent overview page. Each skill is an island.
5. **Rigid hub ownership** — ADR-121's `role: primary/extension` was a step toward composition but only handles sub-route mounting, not widget contribution or overview assembly.

### Current State

- **14 bundles** containing **40 skills**, each with its own `augur.yaml`
- **40 unique hub IDs** → 40 sidebar entries
- Schema version: `1.0` (implicit, no version field)
- `DashboardYaml` type in `lib/plugin-schema/types.ts` defines: `hub`, `tabs`, `modals`, `actions`, `mcp_tools`, `dependencies`, `data_dir`
- `mount-plugins.ts` copies dashboard files into `src/app/{hub.id}/`
- `HubRenderer.tsx` renders hub header + tab navigation
- Sidebar derived from hub registry (generated by `generate-hub-registry.ts`)

### Desired Outcome

- **14 sidebar entries** (one per bundle) instead of 40
- Each bundle gets an **auto-generated overview page** with widgets from all contributing skills
- Skills declare **widgets** (summary cards for the overview) and **pages** (full tab content)
- Pages auto-cascade as **tabs** under the bundle hub
- Cross-bundle contributions are explicitly supported (e.g., `linkedin-writer` contributing to both `career` and `creative` hubs)
- Bundle-scoped **search** aggregates across all skills in the bundle

## Decision

### Schema v3.0: Contribution Model

Replace the current per-skill hub ownership with a **contribution model** where skills declare what they contribute to a hub rather than owning it outright.

### 1. New `augur.yaml` Schema

#### Primary Skill (defines the hub)

One skill per bundle declares the `hub:` block. This is the hub owner.

```yaml
version: '3.0'
skill: career
contributes_to: career          # hub ID (defaults to bundle name)

hub:                             # Only ONE skill per hub defines this
  title: Career Hub
  subtitle: Job search, interviews, and professional growth
  icon: Briefcase
  category: career
  overview:                      # Overview page configuration
    search: true                 # Enable bundle-scoped search
    layout: masonry              # Widget layout: masonry | grid | stack
    empty_state: "No career data yet. Start by adding a job application."

contributions:
  widgets:
    - id: job-pipeline
      title: Job Pipeline
      component: JobPipelineWidget    # TSX component name
      size: half                      # full | half | third | quarter
      priority: 10                    # Lower = higher on page
      data_source: /api/career/pipeline/stats
    - id: interview-prep
      title: Interview Prep
      component: InterviewPrepWidget
      size: quarter
      priority: 20

  pages:
    - id: pipeline
      title: Pipeline
      icon: Briefcase
    - id: companies
      title: Companies
      icon: Building2
    - id: scoring
      title: Scoring
      icon: BarChart3
    - id: interview
      title: Interview
      icon: MessageSquare
    - id: star
      title: STAR Stories
      icon: Star
    - id: resume
      title: Resume
      icon: FileText
    - id: profile
      title: Profile
      icon: User

  search:
    index_fields: [title, company, status, location]
    display_fields: [title, company, status]

  actions:                        # Moved from top-level to contributions
    - id: add-job
      title: Add Job
      icon: Plus
      mcp_tool: career-add-job

tabs: []                          # DEPRECATED — use contributions.pages
modals: {}                        # Kept at top level (modal definitions are skill-scoped)
mcp_tools:                        # Kept at top level (tool registration is skill-scoped)
  - brightdata-scrape
  - brightdata-search
dependencies:
  required: []
  optional: [knowledge]
data_dir: job-analyzer
```

#### Contributing Skill (adds to existing hub)

```yaml
version: '3.0'
skill: linkedin-writer
contributes_to: career            # Contributes to the career hub

contributions:
  widgets:
    - id: linkedin-posts
      title: Recent Posts
      component: LinkedInPostsWidget
      size: third
      priority: 25
      data_source: /api/career/linkedin/recent

  pages:
    - id: linkedin-writer
      title: LinkedIn
      icon: Linkedin

  search:
    index_fields: [title, content, status]
    display_fields: [title, status, published_at]

mcp_tools:
  - list-linkedin-posts
  - get-linkedin-post
  - create-linkedin-post
  - update-linkedin-post-status
data_dir: linkedin-writer
```

#### Cross-Hub Contribution

A skill can contribute to a hub outside its own bundle:

```yaml
version: '3.0'
skill: wealth
contributes_to: finance           # Primary hub: finance (same bundle)

cross_hub:                        # Optional: contribute widgets to other hubs
  - hub: venture
    widgets:
      - id: portfolio-summary
        title: Portfolio
        component: PortfolioMiniWidget
        size: quarter
        priority: 50
```

### 2. Hub Assembly Pipeline

The hub assembly runs at build time in `mount-plugins.ts`:

```
Step 1: Scan all augur.yaml files
Step 2: Group by contributes_to field
Step 3: For each hub ID:
  a. Find the skill with hub: block → hub owner
  b. If no hub: block, auto-generate from bundle metadata
  c. Collect all contributions (widgets, pages, search, actions)
  d. Sort widgets by priority
  e. Merge pages into tab list
  f. Merge search index_fields
  g. Apply cross_hub contributions from other bundles
Step 4: Generate assembled hub config → used by HubRenderer
Step 5: Generate overview page component with widget slots
Step 6: Mount skill dashboard dirs as tab sub-routes
```

### 3. Auto-Generated Overview Page

Each hub gets an auto-generated overview page at `/{hub_id}/` that:

1. Renders a **search bar** (if `overview.search: true`) scoped to the bundle
2. Renders **widget grid** using the assembled widget list, sorted by priority
3. Uses the layout specified in `overview.layout`
4. Handles empty states per `overview.empty_state`

Widget components are loaded from their skill's dashboard directory:
- `plugins/{bundle}/skills/{skill}/dashboard/widgets/{WidgetComponent}.tsx`

The overview page is generated as:
```tsx
// Auto-generated: src/app/{hub_id}/page.tsx
import { HubOverview } from '@/components/plugin/HubOverview';

export default function Page() {
  return <HubOverview hubId="{hub_id}" />;
}
```

`HubOverview` is a new shared component that:
- Reads the assembled hub config at runtime
- Dynamically imports widget components from the registry
- Renders the widget grid with the configured layout
- Provides bundle-scoped search

### 4. Widget Component Standard

All widget components follow a standard interface:

```typescript
export interface WidgetProps {
  hubId: string;
  skillId: string;
  dataSource?: string;    // API endpoint for data
  size: 'full' | 'half' | 'third' | 'quarter';
}

// Example widget
export function JobPipelineWidget({ hubId, dataSource, size }: WidgetProps) {
  const { data } = useSWR(dataSource);
  return (
    <WidgetCard title="Job Pipeline" size={size}>
      {/* Widget content */}
    </WidgetCard>
  );
}
```

### 5. Tab Cascading

Pages declared in `contributions.pages` automatically become tabs:

- Tab order follows declaration order within each skill
- Primary skill's pages come first, then contributing skills in alphabetical order
- The overview tab is always first (auto-inserted)
- Tab ID = page ID, tab label = page title, tab icon = page icon

### 6. Sidebar Reduction

The sidebar generator reads assembled hub configs instead of individual skill configs:

- **Before**: 40 entries (one per `hub.id`)
- **After**: 14 entries (one per `contributes_to` target, which defaults to bundle name)
- Each sidebar entry links to `/{hub_id}/` (the overview page)
- Category grouping uses the bundle directory name (already implemented in ADR-105)

### 7. Type System Updates

```typescript
// lib/plugin-schema/types.ts — Schema v3.0 additions

export interface WidgetDefinition {
  id: string;
  title: string;
  component: string;           // TSX component name
  size: 'full' | 'half' | 'third' | 'quarter';
  priority: number;            // Lower = higher on page
  data_source?: string;        // API endpoint
  refresh_interval?: number;   // Seconds, 0 = no auto-refresh
}

export interface PageDefinition {
  id: string;
  title: string;
  icon?: string;
}

export interface SearchContribution {
  index_fields: string[];
  display_fields?: string[];
}

export interface ContributionBlock {
  widgets?: WidgetDefinition[];
  pages?: PageDefinition[];
  search?: SearchContribution;
  actions?: ActionDefinition[];
}

export interface CrossHubContribution {
  hub: string;
  widgets?: WidgetDefinition[];
}

export interface OverviewConfig {
  search?: boolean;
  layout?: 'masonry' | 'grid' | 'stack';
  empty_state?: string;
}

// Updated DashboardYaml
export interface DashboardYaml {
  version?: string;                    // '3.0' for new schema
  skill?: string;                      // Skill identifier
  contributes_to?: string;             // Hub ID to contribute to
  hub?: HubDefinition & {
    overview?: OverviewConfig;
  };
  contributions?: ContributionBlock;
  cross_hub?: CrossHubContribution[];
  tabs?: TabDefinition[];              // DEPRECATED in v3.0, kept for compat
  modals?: Record<string, ModalDefinition>;
  mcp_tools?: string[];
  mcp?: { tools?: string[]; max_tools?: number };
  dependencies?: { required?: string[]; optional?: string[] };
  data_dir?: string;
  // Deprecated v1.0 fields kept for migration period
  actions?: ActionDefinition[];
  item_actions?: ItemActionDefinition[];
  bridge?: { enabled: boolean };
  mode?: string;
}

// Assembled hub (output of assembly pipeline)
export interface AssembledHub {
  id: string;
  title: string;
  subtitle: string;
  icon: string;
  category: string;
  overview: OverviewConfig;
  widgets: (WidgetDefinition & { skill: string })[];
  tabs: (PageDefinition & { skill: string })[];
  search: { index_fields: string[]; display_fields: string[] };
  skills: string[];            // All contributing skill IDs
  owner: string;               // Skill that defines hub: block
  mcp_tools: string[];         // Aggregated from all skills
}
```

### 8. Migration Strategy

All 40 `augur.yaml` files migrate to v3.0 in a single pass:

**Step 1**: Add `version: '3.0'`, `skill:`, and `contributes_to:` fields

**Step 3**: Move `actions` to `contributions.actions`
**Step 4**: For primary skills (one per bundle), add `hub:` block extracted from current `hub:` field
**Step 5**: For non-primary skills, remove `hub:` block (they only contribute)

- Add hub assembly step after scanning augur.yaml files
- Group skills by `contributes_to` instead of `hub.id`
- Generate overview page for each assembled hub
- Mount skill dashboards as sub-routes under `/{hub_id}/{page_id}/`

#### `generate-hub-registry.ts`
- Output assembled hubs (14) instead of raw hubs (40)
- Include widget counts and contributing skill lists

#### `generate-tab-registry.ts`
- Read assembled hub tabs instead of per-skill tabs
- Include overview tab as first entry

#### `generate-page-manifest.ts`
- Report assembled hubs with aggregated tool counts

### 10. New Components

#### `HubOverview.tsx`
Shared component that renders the auto-generated overview page:
- Widget grid with configurable layout
- Bundle-scoped search bar
- Empty state handling
- Dynamic widget loading from registry

#### `WidgetCard.tsx`
Standard wrapper for all widgets:
- Consistent sizing (full/half/third/quarter)
- Loading state
- Error boundary per widget
- Refresh button (if `refresh_interval` set)

#### `WidgetRegistry.ts`
Maps widget component names to lazy-loaded imports:
- Generated at build time from assembled hub configs
- Each widget is `React.lazy(() => import(...))`

### 11. Backward Compatibility

The migration is **not** backward compatible — v1.0 schema is fully replaced:

- `tabs:` field is ignored when `contributions.pages` exists
- `hub.role` and `hub.extends` are removed (replaced by `contributes_to`)
- `hub.id` is replaced by `contributes_to` as the grouping key
- All 40 augur.yaml files are migrated in a single commit

Build scripts detect schema version and error on v1.0 files after migration.

## Consequences

### Positive

1. **Sidebar reduced from 40 → 14 items** — Dramatically simpler navigation
2. **Auto-generated overview pages** — Every bundle gets a summary without manual coding
3. **Widget composition** — Skills contribute summary cards to parent overview
4. **Bundle-scoped search** — Search across all skills in a bundle from one search bar
5. **Cleaner ownership model** — `contributes_to` is simpler than `role: primary/extension`
6. **Cross-hub contributions** — Skills can add widgets to hubs outside their bundle
7. **Standard widget interface** — Consistent sizing, loading, error handling
8. **Reduced boilerplate** — Contributing skills don't repeat hub title/icon/subtitle

### Negative

1. **Breaking migration** — All 40 augur.yaml files change at once, no gradual rollout
2. **Widget development required** — Each skill needs at least one widget component (initially empty/placeholder)
3. **Build complexity increases** — Assembly pipeline adds a build step
4. **mount-plugins.ts grows** — Already 1327 lines, adds ~200 more for assembly
5. **No standalone skill pages** — Skills that don't fit a bundle need a synthetic bundle

### Neutral

1. `HubRenderer.tsx` still renders tab navigation — just reads from assembled config instead
2. `plugin-runtime` components (`StatsGrid`, `EntityTable`) unchanged — used inside widgets
3. MCP tool registration unchanged — still per-skill in `mcp_tools:`
4. API routes unchanged — still per-skill in `src/dashboard/app/api/`

## Alternatives Considered

### Alternative A: Flat Widget+Page Declarations

Each skill declares `widgets:` and `pages:` at the top level, with a separate `hub_config.yaml` per bundle.

**Rejected because**: Requires a new file type (`hub_config.yaml`) maintained separately from skill configs. Two sources of truth for hub metadata. No natural place for cross-hub contributions.

### Alternative B: Hub Template + Skill Slots

Define hub templates with named slots, skills fill specific slots.

**Rejected because**: Over-engineered for the current need. Slot-based composition adds cognitive overhead — skill authors must know which slots exist. Template versioning adds maintenance burden. The contribution model achieves the same result with a simpler mental model.

### Alternative C: Keep Current Schema, Add Nav Grouping

Group existing 40 hub IDs into categories in the sidebar without changing the schema.

**Rejected because**: Doesn't solve the overview page problem. Doesn't enable widget composition. Sidebar grouping without content aggregation is cosmetic — users still navigate 40 separate pages. Doesn't reduce boilerplate.
