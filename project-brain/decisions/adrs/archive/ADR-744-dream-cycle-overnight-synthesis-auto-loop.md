# ADR-744: Dream Cycle — Cross-Client Overnight Synthesis Routine

## Status

Implemented (2026-05-16) — `shared-vault/skills/dream/` ships the routine
(`commands/dream.md`), nine `dream-*` MCP tools, the `aug dream <verb>` CLI,
the Codex schedule-seed (auto-activated by `sync_agents`), and the
projection façade for the remaining clients. Real-vault smoke produced a
report at `<documents>/reports/dream/<date>.md` covering all five phases.

## Context

Augur runs auto-loops for hygiene, quality, security, and observability, but there is **no coordinated overnight synthesis pass** that compounds the second brain on a regular cadence. The wiki freshness ADR (ADR-731) consolidated memory synthesis, but the *trigger* and *orchestration* of a full compounding pass is unspecified.

A reference implementation (gbrain) runs an 11-phase "Dream Cycle" overnight (synthesis, pattern extraction, citation fixing, orphan cleanup, entity tiering). Augur needs the same compounding *shape*, but the trigger model in gbrain (its own daemon calls its own LLM tier) is not compatible with Augur's harness model (Rule #11, Rule #19, `feedback_vendor_neutral_design`).

The right trigger for Augur is the **client's own routine system** — Claude Code `/schedule` and `/loop`, Codex scheduled agents, Gemini routine equivalents. Each supported client already ships a native routine surface. Augur authors the dream cycle **once** and projects it per-client via `sync_agents`, analogous to how skills, agents, and constitutions are projected today (ADR-670, cross-client bundle architecture). The client schedules the routine, runs it in its own session, calls Augur's MCP tools for deterministic work, and reasons in its own LLM context for judgment work. Augur owns no scheduling and no LLM call.

This makes Rule #11/#19 enforced **by construction**: the LLM that reasons is the client's, the trigger that fires is the client's, and Augur's role is exposing MCP entry points and recording state.

## Decision

Author the dream cycle once in Augur and project it as a **scheduled routine** into every supported AI client via `sync_agents`. The routine runs inside the client's own session on the client's schedule. The routine calls Augur MCP tools for deterministic phases and reasons inline (no `oneshot` dispatch — the client is *already* running the routine in its session) for judgment phases. Each phase records a job via the ADR-743 ledger. The cycle produces a human-readable report at `get_documents_dir()/reports/dream/<date>.md`.

Concretely:

**Routine authoring (once, in Augur):**

- Routine source lives in a dedicated `dream/` skill at `shared-vault/skills/dream/commands/dream.md` (settled in the spec; the skill delegates deterministic phases to sibling tools rather than reimplementing them).
- The routine body is a multi-step prompt: deterministic-phase MCP calls + inline judgment prompts.
- Per-client routine artifacts generated by `sync_agents`:
  - Claude Code: registered through `/schedule` or `/loop` surface
  - Codex: registered as a Codex scheduled agent
  - Gemini: equivalent native surface
  - Cursor, Copilot: per current client capability; degrade gracefully when no native routine surface exists

**Deterministic phases (Augur MCP tools, zero LLM cost, called by the routine):**

1. **Orphan cleanup** — wiki pages with no inbound links and a low timeline count are flagged for review (not auto-deleted).
2. **Citation fixing** — timeline entries (ADR-740) pointing to dead source-card / vault URIs are flagged.
3. **Stale-cache GC** — rebuildable indexes older than retention threshold (default 30 days) are purged from `get_cache_dir()`.
4. **Entity tiering recompute** (ADR-738) — re-runs tier classification across all entities.

**Judgment phases (run inline in the client's session, no Augur-side LLM call):**

5. **Compiled-truth refresh** (ADR-740) — for pages flagged stale, the client reads recent timeline entries via MCP and proposes an updated compiled-truth section. Output is a proposal, not an automatic write.
6. **Pattern extraction** — the client surveys recent ingestions and proposes new wiki seeds.
7. **Wiki concept merging** — the client reviews high-similarity page pairs and proposes merges.

**Orchestration:**

- Every phase opens a job via `jobs-submit` (ADR-743). Phase start / heartbeat / completion append events to the ledger.
- Phase order, retries, and skips configurable in the `dream/` skill's `config.yaml` (skill-local — only the dream routine reads it; not central config).
- Failure of any phase does not block subsequent deterministic phases.
- Output report consolidates phase results and links proposals into the user's normal proposal review flow.

New MCP tools (called by the routine, not by a daemon): `dream-orphans`, `dream-dead-citations`, `dream-cache-gc`, `dream-stale-pages`, `dream-merge-candidates`, `dream-report-write`, `dream-status`, `dream-last-report`, `dream-config`. Entity-tier recompute is **delegated** to ADR-738's `entity-tier-recompute` — not a new dream tool. `dream-cache-gc` is a filesystem GC of allowlisted rebuildable index caches under `get_cache_dir()` with a retention threshold (default 30 days, configurable in skill-local config); it opportunistically signals the in-memory `cache-control` skill-cache invalidator after a non-empty purge — but is NOT a thin delegate to it (that tool flushes the in-memory skill cache; it does not GC disk files). CLI-default per surface-decision-matrix; routine-callable always.

## Non-Goals

- **No Augur-side scheduling for the dream cycle.** Augur does not own the cron. The client's routine system schedules it. `launchd` and Task Scheduler continue to schedule *other* auto-loops; the dream cycle specifically delegates scheduling to the client.
- **No direct LLM calls from Augur during dream** — enforced by construction, since the client runs the routine and owns the LLM context.
- **No autonomous destructive operations.** Orphans, dead citations, and merges are proposals; the user confirms before any delete/merge.
- No mutation of compiled-truth sections without explicit approval (ADR-740 enforces this).
- No replacement of existing hygiene/quality loops — dream is additive, focused on knowledge compounding specifically.
- No cloud routine execution — the routine runs on the user's laptop in the user's client session.

## Consequences

- Builds directly on ADR-738 (tiering), ADR-740 (timeline / compiled truth), ADR-743 (ledger), ADR-670 (cross-client projection).
- `sync_agents` extends to project a new artifact class: **scheduled routines per client**. Clients without a native routine surface (or with a weaker one) get a documented fallback (e.g. a "run dream now" slash command the user fires manually).
- The daemon's role for dream shrinks to **MCP entry points + ledger**. No daemon-side scheduling logic for dream.
- New report directory `get_documents_dir()/reports/dream/`.
- `architecture-daemon.md` gains a "compounding routines" section that explicitly distinguishes Augur-scheduled auto-loops from client-scheduled routines.
- Eval harness (ADR-742) can A/B compare retrieval before/after dream cycles.
- Cross-client parity: if Claude Code adds a routine feature tomorrow that Codex doesn't have, the dream routine still works under both because sync_agents projects the right artifact per client.
