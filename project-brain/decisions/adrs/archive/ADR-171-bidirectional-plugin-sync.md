# ADR-171: Bidirectional Claude Plugin Sync

## Context

Augur's `sync_agents.py` (2,111 lines) distributes skills and workflows **outward** to 11 IDE adapters (Claude Code, Cursor, Windsurf, Copilot, Gemini, OpenCode, Kimi, Antigravity, Codex, Cline, Claude Desktop). However, the 11 installed Claude Code plugins (`superpowers`, `feature-dev`, `frontend-design`, `code-review`, `code-simplifier`, `context7`, `playwright`, `pyright-lsp`, `claude-md-management`, `ralph-loop`, `github`) in `~/.claude/plugins/cache/claude-plugins-official/` exist in a completely isolated silo:

1. **Invisible to the ai_bridge** — `registry.yaml` has zero knowledge of Claude plugin capabilities, agents, or skills
2. **Unavailable to non-Claude clients** — Cursor, Windsurf, Copilot, Codex etc. cannot access any Claude plugin functionality
3. **Overlapping without resolution** — 3 plugins directly compete with Augur skills:
   - `feature-dev` (agents: code-explorer, code-architect, code-reviewer) ↔ `developer` skill
   - `frontend-design` (creative design system) ↔ `frontend` skill
   - `code-review` (PR-level review) ↔ `validator` skill

The `/ops-sync` pipeline is currently one-directional (outward only). Meanwhile, Augur's 46+ slash commands are invisible to Claude Code's native skill discovery — users cannot type `/ask` or `/dev-build` and have Claude find them without explicit CLAUDE.md instructions.

**Quantified impact**: 11 plugins × 10 non-Claude adapters = 110 potential capability deliveries that don't happen today. 46 slash commands × 1 missing export = 46 discoverable skills lost.

## Decision

Add a **bidirectional plugin sync** as Phase 3 in `sync_agents.py`, using declarative per-skill manifests in `augur.yaml` following Critical Rule #1 (plugin decentralization).

### Component 1: Inward Sync — Plugin Discovery & Import

**Action**: Create `discover_claude_plugins()` function in `sync_agents.py`

Scans `~/.claude/plugins/cache/claude-plugins-official/*/` and extracts:
- Plugin manifest from `.claude-plugin/plugin.json` (name, description)
- Agent definitions from `agents/*.md` (frontmatter + content)
- Skill definitions from `skills/*/SKILL.md` (superpowers-style nested layout)
- Command definitions from `commands/*.md` (feature-dev-style flat layout)

**Action**: Create `assemble_claude_plugins()` function

Writes `config/dashboard/generated/assembled_claude_plugins.json` — read-only cache following the `assembled_hubs.json` pattern. Contains lean metadata (no full content) for dashboard and registry consumption.

**Action**: Create `resolve_overlaps()` function

Reads `claude_plugins.imports` from each skill's `augur.yaml` and applies merge strategies:
- `augment` (default) — Claude agents available as supplementary tools alongside Augur skill
- `replace` — Claude plugin fully replaces equivalent Augur capability
- `ignore` — Plugin present but not imported for this skill

Cherry-pick support: `cherry_pick: [agents/code-explorer, agents/code-architect]` limits which items get imported.

**Files created/modified:**
- Modify: `plugins/ai/skills/ai_bridge/scripts/sync_agents.py` — add `_parse_md_frontmatter()`, `discover_claude_plugins()`, `assemble_claude_plugins()`, `resolve_overlaps()`
- Create: `config/dashboard/generated/assembled_claude_plugins.json` (auto-generated)

### Component 2: Outward Sync — Command Export

**Action**: Create `export_augur_skills()` function in `sync_agents.py`

Reads `_iter_all_commands()` output and generates `~/.claude/skills/{command}/SKILL.md` per slash command:
- Filtered by visibility tier (core/dev/orch/test/ops exported; hidden excluded)
- Auto-generated header: `<!-- AUTO-GENERATED BY sync_agents.py (ADR-171) -->`
- Preserves user-created skills (skips files without AUTO-GENERATED header)
- Tracked in `.agent/ide-manifest.json` for stale cleanup

**Files created/modified:**
- Modify: `plugins/ai/skills/ai_bridge/scripts/sync_agents.py` — add `export_augur_skills()`, `EXPORT_HEADER` constant
- Create: `~/.claude/skills/{command}/SKILL.md` (46+ auto-generated files)

### Component 3: Multi-Client Agent Distribution

**Action**: Create `distribute_imported_agents()` function in `sync_agents.py`

When a Claude plugin agent is imported via `augur.yaml`:
1. **Claude Code** — already available natively; Augur skill references by `subagent_type`
2. **Cursor** — agent prompt written to `.cursor/skills/{agent-name}.md` (Claude frontmatter stripped)
3. **Windsurf** — agent prompt written to `.windsurf/workflows/{agent-name}.md`
4. **Copilot** — agent prompt written to `.github/skills/{agent-name}.md`
5. **Other adapters** — follow existing adapter-specific path patterns
6. **Non-agent IDEs** (no dispatch) — capabilities described as instructions in rules file

Uses existing `strip_claude_frontmatter_fields()` for non-Claude adapters.

**Files created/modified:**
- Modify: `plugins/ai/skills/ai_bridge/scripts/sync_agents.py` — add `distribute_imported_agents()`, `_ADAPTER_AGENT_PATHS` mapping
- Create: adapter-specific agent files (auto-generated per adapter)

### Component 4: Overlap Resolution Declarations

**Action**: Add `claude_plugins:` section to 3 overlapping skill `augur.yaml` files

**developer** (`plugins/dev/skills/developer/augur.yaml`):
```yaml
claude_plugins:
  imports:
    - source: feature-dev
      merge: augment
      cherry_pick:
        - agents/code-explorer
        - agents/code-architect
        - agents/code-reviewer
```

**frontend** (`plugins/dev/skills/frontend/augur.yaml`):
```yaml
claude_plugins:
  imports:
    - source: frontend-design
      merge: augment
```

**validator** (`plugins/dev/skills/validator/augur.yaml`):
```yaml
claude_plugins:
  imports:
    - source: code-review
      merge: augment
```

### Component 5: Pipeline Integration

**Action**: Wire Phase 3 into `main()` function

Add `--plugins` argument and Phase 3 block after existing memory sync:
1. `discover_claude_plugins(CLAUDE_PLUGINS_CACHE)` → scan installed plugins
2. `assemble_claude_plugins(plugins, ASSEMBLED_PLUGINS_PATH)` → write cache
3. `resolve_overlaps(plugins, PROJECT_ROOT)` → apply merge strategies
4. `export_augur_skills(commands, CLAUDE_SKILLS_EXPORT_DIR)` → export commands
5. `distribute_imported_agents(resolved, PROJECT_ROOT, adapter)` → distribute to all IDEs
6. Update `GENERATED_FILES` list → manifest tracking

**Constants added:**
- `CLAUDE_PLUGINS_CACHE = Path.home() / ".claude" / "plugins" / "cache" / "claude-plugins-official"`
- `ASSEMBLED_PLUGINS_PATH = PROJECT_ROOT / "config" / "dashboard" / "generated" / "assembled_claude_plugins.json"`
- `CLAUDE_SKILLS_EXPORT_DIR = Path.home() / ".claude" / "skills"`

## Consequences

### Positive

- All 11 installed Claude plugins become available across all 11 IDE clients (110 new capability deliveries)
- 46+ Augur slash commands discoverable as native Claude Code skills
- Overlapping capabilities merged (best of both) instead of silently conflicting
- Per-skill `augur.yaml` declarations follow Critical Rule #1 (decentralization)
- No central plugin registry to maintain — discovery is filesystem-based
- Existing sync phases completely unchanged — Phase 3 is purely additive
- User-created `~/.claude/skills/` files never overwritten (AUTO-GENERATED header check)

### Negative

- Coupled to Claude plugin cache directory structure (`~/.claude/plugins/cache/claude-plugins-official/`) — must update if Claude Code changes this convention
- Skills with overlaps need manual `augur.yaml` declarations (3 files initially, O(1) ongoing)
- Imported agent prompts designed for Claude Code may need adaptation for non-Claude IDEs (frontmatter stripping handles most cases, but behavioral differences possible)
- `assembled_claude_plugins.json` is another generated file to track (though it follows proven pattern)

### Neutral

- Non-overlapping plugins require zero configuration — imported wholesale
- Plugin cache path is a convention, not a contract — parameterized via `CLAUDE_PLUGINS_CACHE` constant for easy update
- The `_parse_md_frontmatter()` helper duplicates light YAML parsing that may exist elsewhere, but keeps `sync_agents.py` self-contained

## Alternatives Considered

### Alternative A: Plugin Bridge Adapter

Add a new `PluginBridgeAdapter` class to `sync_agents.py` alongside the existing 11 IDE adapters, handling both inward and outward sync through the adapter interface.

**Rejected because**: Centralizes all plugin mapping knowledge into a single adapter class, violating Critical Rule #1. Import decisions should live in each skill's `augur.yaml`, not in a central adapter. The adapter pattern is designed for IDE-specific output formatting, not for cross-system integration logic.

### Alternative B: Standalone Plugin Sync Module

Create a separate `plugin_sync.py` module called by `sync_agents.py` as a new phase. Clean separation of concerns with independent testability.

**Rejected because**: Still requires centralized mapping logic in the module. The declarative manifest approach (Approach C) distributes control to individual skills via `augur.yaml` declarations, which is more aligned with the decentralization principle and the precedent set by ADR-163 and ADR-130's action discovery pattern.
