# Hub Tab Navigation Redesign

## Problem

Hub pages currently have no horizontal tab navigation. After hub root pages were removed (ADR-406), the only way to navigate between pages within a hub is via the sidebar, which shows one vertical entry per skill. Custom pages, auto pages, and blocks are all either hidden or mixed together with no visual distinction. Users cannot discover or access most pages without knowing the URL.

## Solution

Add a horizontal tab bar at the top of every hub page that:
- Shows **custom pages** (`page_type: custom`) as primary horizontal tabs with responsive overflow into a "More" dropdown
- Adds a **Blocks** dropdown button (right-anchored) listing all `contributions.blocks` for the hub, grouped by skill
- Adds an **Auto** dropdown button (right-anchored) listing all `page_type: auto` pages for the hub, grouped by skill
- Hides Blocks/Auto buttons when a hub has none of that type

## Data Model

### Registry Changes

The generated tab registry (`lib/tabs/generated-registry.ts`) changes from a flat tab list to a three-way split:

```typescript
// Current
interface HubConfig {
  tabs: TabItem[];
  overflow?: TabItem[];
  // ...existing fields
}

// Proposed
interface HubConfig {
  tabs: TabItem[];           // custom pages that fit in the bar
  overflow?: TabItem[];      // custom pages that overflow
  blocks: BlockNavItem[];    // from contributions.blocks
  autoPages: TabItem[];      // page_type: auto pages
  // ...existing fields
}

interface BlockNavItem {
  id: string;
  label: string;
  icon: string;
  skill: string;             // grouping key
  expandTo?: string;          // route to navigate to (if block defines one)
  render?: string;            // block render type (maps from BlockDefinition.render)
  component?: string;         // component name (maps from BlockDefinition.component)
}
```

### Data Source

- **Custom pages**: discovered from filesystem with `page_type: custom` in augur.yaml `contributions.pages`
- **Auto pages**: discovered from filesystem with `page_type: auto` in augur.yaml `contributions.pages`
- **Blocks**: from `contributions.blocks` in augur.yaml

### Prerequisites: Scanner & Schema Changes

**`page_type` must be added to `DiscoveredPage`:** The scanner (`scanner.ts`) currently extracts only `label`, `icon`, `order`, `devOnly`, `visible` from `contributions.pages` into `DiscoveredPage.overrides`. The `page_type` field exists in `PageDefinition` but is silently dropped during discovery. Fix: add `page_type?: "custom" | "auto"` to `DiscoveredPage.overrides` and update both the array and map parse branches in the scanner to extract it. Without this, the custom/auto split is impossible.

**`BlockDefinition` field mapping:** `BlockNavItem.expandTo` does not exist in `BlockDefinition` today. Options:
- Add `expand_to?: string` to `BlockDefinition` in `types.ts` and to the augur.yaml schema for blocks
- Map existing fields: `render` → `BlockNavItem.render`, `component` → `BlockNavItem.component`
- For blocks without `expand_to`, use inline rendering via `BlockRenderer` with the block's `render`/`component` config

## Component Architecture

### Component Tree

```
app/{hub}/layout.tsx (generated by mount-plugins)
├── HubHeaderSection          — NEW: extracted from HubRenderer header block (lines 127-168)
├── HubTabBar                 — NEW: full tab bar component
│   ├── TabList               — horizontal custom page tabs
│   ├── OverflowDropdown      — "More ▾" for custom pages that don't fit
│   ├── BlocksDropdown        — "Blocks ▾" right-anchored, grouped by skill
│   └── AutoPagesDropdown     — "Auto ▾" right-anchored, grouped by skill
└── {children}                — page content from Next.js routing
```

### HubTabBar

The primary new component. Replaces `UnifiedHubTabs` for hub-level navigation.

**Props:**
```typescript
interface HubTabBarProps {
  tabs: TabItem[];              // custom page tabs (visible)
  overflow?: TabItem[];         // custom page tabs (overflow)
  blocks: BlockNavItem[];       // block items for dropdown
  autoPages: TabItem[];         // auto page items for dropdown
  basePath: string;             // hub base path for active detection
}
```

**Layout:** Custom tabs flow left-to-right. ResizeObserver measures available width; tabs that don't fit move into "More ▾". Blocks and Auto dropdown buttons are right-anchored with a flex spacer, always visible regardless of custom tab count.

**Responsive behavior:** The two dropdown buttons reserve fixed width. Custom tabs fill remaining space. When viewport shrinks, custom tabs move into "More" overflow before any clipping occurs.

### BlocksDropdown

- Grouped by skill (uppercase skill name as section header)
- Search filter at top (useful for hubs with many blocks, e.g., productivity has 19)
- Each item shows: block icon, label, and a navigation indicator
  - `→` = has `expandTo` route, click navigates
  - `⤢` = no expandTo, click renders block inline in a panel below the tab bar
- Footer legend explaining the indicators
- Closes on click-outside or after selection

### AutoPagesDropdown

- Grouped by skill (same section header style)
- No search filter (auto pages are fewer in number)
- Every click navigates to the page route (e.g., `/productivity/apple/notes`)
- Closes on click-outside or after selection

### OverflowDropdown ("More")

- Simple flat list of custom page links that didn't fit in the tab bar
- Same style as visible tabs — click navigates
- Only renders when there are overflow items

### Empty States

- Hub has 0 blocks → Blocks button hidden
- Hub has 0 auto pages → Auto button hidden
- Hub has 0 custom pages → only dropdown buttons render (no tab list, no "More")

### Validation Guard Update

`generate-tab-registry.ts` line 110 validates `config.tabs.length === 0` as an error. With the three-way split, `tabs` may be empty for hubs that only have auto pages or blocks. The validation must be relaxed: a hub is valid if it has any of `tabs`, `blocks`, or `autoPages` non-empty.

## Hub Layout Generation

Hub layouts are **generated by the mount script** as a distinct assembly artifact (same category as `NestedSkillLayout` in `assembleAndWriteHubs`). No manual layout files to maintain.

### Server/Client Boundary

`HubTabBar` is a client component (uses `usePathname`, `ResizeObserver`, `useState`). The generated layout must include `"use client"` — following the same pattern as `NotificationBadgeTabs` where a thin client wrapper owns the interactive shell.

### Interaction with `isSkillOnly` Rule

`copier.ts` (line 742) enforces that plugin `layout.tsx` files only copy to `app/{hub}/{skill}/`, not to `app/{hub}/`. The generated hub-root `layout.tsx` is a separate assembly artifact — it is **not** a plugin-sourced file and is not subject to `isSkillOnly`. It is written during the assembly phase, after plugin files are copied.

The 26 existing skill-level `layout.tsx` pass-throughs (bare `<>{children}</>` wrappers) remain at `app/{hub}/{skill}/layout.tsx` and are harmless — they don't render a tab bar, so no double-rendering occurs. Next.js nests them: hub layout (header + tabs) → skill layout (pass-through) → page content.

### Generation Flow

During `mount-plugins` / `npm run build`:

1. `generate-tab-registry.ts` processes augur.yaml files and splits pages by type
2. `assembleAndWriteHubs` (in mount-plugins) generates a `layout.tsx` at `app/{hub}/layout.tsx` for each hub:
   - Marked `"use client"`
   - Imports `HubTabBar` from `@/components/HubTabBar`
   - Imports hub config from the generated registry
   - Renders `HubHeaderSection` + `HubTabBar` + `{children}`

Generated layout template (conceptual):
```tsx
"use client";

import { HubTabBar } from '@/components/HubTabBar';
import { HubHeaderSection } from '@/components/plugin/HubHeaderSection';
import { pluginTabRegistry } from '@/lib/tabs/generated-registry';

export default function HubLayout({ children }: { children: React.ReactNode }) {
  const config = pluginTabRegistry['{{hubId}}'];
  return (
    <>
      <HubHeaderSection hubId="{{hubId}}" />
      <HubTabBar
        tabs={config.tabs}
        overflow={config.overflow}
        blocks={config.blocks}
        autoPages={config.autoPages}
        basePath={config.basePath}
      />
      {children}
    </>
  );
}
```

## Sidebar Navigation Update

`navigation.ts` `pluginToNavItem()` currently deduplicates to one entry per skill (keeping the shallowest route). The tab bar now handles intra-hub navigation, so the sidebar dedup logic can remain as-is — one entry per skill is appropriate for the sidebar's role as hub-level navigation. The tab bar handles page-level navigation within each hub. No sidebar change needed.

## Files Changed

| File | Change |
|------|--------|
| `scripts/generate-tab-registry.ts` | Extend local `HubConfig` interface with `blocks`/`autoPages` fields, split pages by `page_type`, populate `blocks` from assembled hub data, relax `validateHubConfig` to accept hubs with only blocks/autoPages |
| `lib/tabs/types.ts` | Add `BlockNavItem` type, add `autoPages` and `blocks` fields to `HubConfig` |
| `components/HubHeaderSection.tsx` | **New** — extracted from `HubRenderer` lines 127-168 (icon, title, subtitle, actions) |
| `components/HubTabBar.tsx` | **New** — full tab bar with responsive overflow + two dropdowns |
| `components/BlocksDropdown.tsx` | **New** — grouped block list with search, expandTo-aware click |
| `components/AutoPagesDropdown.tsx` | **New** — grouped auto page list, click navigates |
| `lib/plugin-discovery/scanner.ts` | Add `page_type` to `DiscoveredPage.overrides`, extract from augur.yaml |
| `lib/plugin-schema/types.ts` | Add `expand_to?: string` to `BlockDefinition` |
| `scripts/mount-plugins.ts` | Generate `layout.tsx` per hub during assembly phase (after plugin copy) |

## Files Unchanged

- `UnifiedHubTabs.tsx` — kept for settings and non-hub usage
- `BlockRenderer.tsx` — unchanged, used for inline block rendering
- `augur.yaml` page definitions — no schema changes (page_type already exists)
- `lib/navigation.ts` — sidebar dedup stays as-is (tab bar handles page-level nav)
- Individual `page.tsx` files — unchanged

## Scale

Across 15 hubs:
- 93 custom pages → primary tab slots
- 55 auto pages → Auto dropdowns
- 136 blocks → Blocks dropdowns

Heaviest hubs: Professional (43 items), Productivity (38 items), Career (35 items).
