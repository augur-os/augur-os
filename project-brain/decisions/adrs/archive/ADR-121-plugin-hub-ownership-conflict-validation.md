# ADR-121: Plugin Hub Ownership and Conflict Validation

## Context

The mount pipeline currently keys plugins by `hub.id` and merges by overwrite semantics. When multiple skills declare the same `hub.id`, whichever plugin is processed last can silently replace another plugin's mounted UI/API routes.

This has created recurring failures:

- Hidden route ownership conflicts discovered only at runtime or in downstream tests.
- Surprise behavior when a secondary skill is interpreted as a full hub owner.
- Fragile conventions for “sub-skills” that rely on manual placement and discipline instead of validated structure.

Recent incidents around duplicated `hub.id` values (for example, multiple skills targeting `career`) confirm this is a systemic mount-lifecycle issue, not an isolated mistake.

## Decision

We will introduce an explicit hub ownership model and enforce it during mount-time.

### 1. Hub roles become explicit

Each `dashboard.yaml` must declare whether it is:

- `primary` — owns the hub root (`/{hubId}`)
- `extension` — contributes sub-routes to an existing hub

For `extension` plugins, required metadata:

- `extends`: target hub id (for example `career`)
- `routePrefix`: unique sub-route segment (for example `linkedin-writer`)

### 2. Pre-mount conflict validation becomes blocking

Before mounting, `mount-plugins` must validate:

- Exactly one `primary` plugin per hub id.
- No `extension` without a matching `primary` owner.
- No duplicate `routePrefix` values under the same `extends` hub.
- No extension route collisions with existing mounted paths.

Any violation fails the mount step with actionable diagnostics (plugin path, hub id, conflicting field).

### 3. Mount behavior follows ownership

- `primary` mounts to `/app/{hubId}` and `/app/api/{hubId}`.
- `extension` mounts only under `/app/{extends}/{routePrefix}` and `/app/api/{extends}/{routePrefix}`.
- `extension` plugins cannot own root-level hub landing routes.

### 4. Validation is enforced in CI

Add/extend dashboard validation checks so ownership conflicts are caught in CI, not only in local builds.

## Consequences

### Positive

- Prevents silent route/API overwrite by design.
- Makes multi-skill hub composition explicit and auditable.
- Reduces firefighting in plugin mount and navigation regressions.
- Improves error quality for contributors adding new skills.

### Negative

- Adds migration work for existing plugins sharing hub ids.
- Introduces new schema requirements in `dashboard.yaml`.
- Requires updates in mount logic and validation tooling.

### Neutral

- Skill-owned UI and plugin-driven routing remain the architecture.
- Existing single-owner hubs continue to behave the same after adding explicit `primary` role.

## Alternatives Considered

### Alternative 1: Keep overwrite semantics and log warnings

Rejected because warnings are easy to miss and do not prevent broken runtime behavior.

### Alternative 2: Namespace all skills by skill id instead of hub id

Rejected because it weakens the hub UX model and breaks intended grouped navigation semantics.

### Alternative 3: Continue relying on manual conventions for sub-skills

Rejected because conventions without schema and validation keep producing regressions.
