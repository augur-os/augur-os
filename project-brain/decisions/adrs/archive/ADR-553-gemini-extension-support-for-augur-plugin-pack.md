# ADR-553: Gemini Extension Support for Augur Plugin Pack

## Context

Augur exposes agent-facing capability surfaces through two paths today. Explicit command wrappers, such as `/dev-loops`, are generated into project-local client files when command markdown declares `x-augur-export-command: true`. Higher-level Augur plugin capabilities, such as `ask`, `search`, and `save`, are packaged through the plugin-pack pipeline for Codex and Claude Desktop Cowork.

This creates an observable Gemini gap. Gemini sees explicitly exported command wrappers because `.gemini/skills/` generation already works, but it does not receive the bundled Augur plugin commands. The root cause is not Gemini skill discovery. The root cause is that Augur does not assemble or install a native Gemini bundle equivalent to the Codex and Cowork plugin-pack targets.

Gemini CLI supports local extensions with `gemini-extension.json`, context files, MCP server configuration, custom commands, and bundled skills. Augur should use this native extension mechanism rather than adding one-off Gemini copies of Augur plugin commands.

## Decision

Augur will add Gemini as a first-class plugin-pack target beside `codex` and `cowork`.

The Gemini target will assemble a native local Gemini extension at `build/gemini/extensions/augur/` and install it into `~/.gemini/extensions/augur/`. The extension will include:

- `gemini-extension.json` with Augur MCP configuration using `--client-id gemini`
- `GEMINI.md` with concise extension context
- selected Augur skills under `skills/<skill>/SKILL.md`
- Gemini custom commands under `commands/augur/*.toml`

The command namespace will be `augur`, producing user-facing commands such as `/augur:ask`, `/augur:search`, and `/augur:save`. Explicit repo command wrappers such as `/dev-loops` remain generated by the existing command-wrapper pipeline and are not moved into the Gemini extension.

The initial Gemini skill filtering profile will match the Codex profile because both targets are local developer-agent environments. If Gemini-specific scope changes are needed later, they will live in `GEMINI_PROFILE`, not in formatter conditionals.

The sync-agents lifecycle will add a `GeminiPluginAdapter` that assembles and installs the Gemini extension. It will be gated with the Gemini dispatch group so disabling Gemini also disables and cleans up the Gemini plugin adapter.

## Consequences

Positive:

- Gemini gets Augur plugin commands through a client-native extension surface.
- The `/ask` gap is fixed at the packaging layer rather than by duplicating command-wrapper metadata.
- Codex, Cowork, and Gemini share the plugin-pack profile and formatter architecture.
- Cleanup stays surgical by deleting only `build/gemini/` and `~/.gemini/extensions/augur/`.

Negative:

- plugin-pack gains one more formatter and test matrix target.
- Gemini command TOML generation must be maintained until command bodies are derived from a single canonical command source.

Neutral:

- Existing `.gemini/skills/` project-local wrappers remain necessary for operational repo commands.
- The dashboard plugin-pack API gains Gemini metadata but does not become an installer.

## Implementation Order

1. Add `GEMINI_PROFILE` to `staging/r3/skills/plugin-pack/scripts/profiles.py` and verify it matches Codex's initial scope.
2. Add `GeminiFormatter` in `staging/r3/skills/plugin-pack/scripts/formatters/gemini.py` with manifest, context, skill, command, and install writers.
3. Add a formatter-owned plugin output directory hook so Gemini can use `extensions/augur` while Codex and Cowork keep `plugins/augur`.
4. Register the `gemini` target in `plugin_assembler.py` and verify assembled output.
5. Add `GeminiPluginAdapter` to `skills/ai/scripts/sync_agents/adapters/` and register it in the sync engine and CLI client filter list.
6. Update plugin-pack documentation and read-only dashboard metadata to show Gemini as a supported target.
7. Verify profile tests, formatter tests, assembler output, adapter tests, and an end-to-end Gemini assembly command.

## Alternatives Considered

### Keep using only `.gemini/skills/` command wrappers

Rejected. This would expose `/ask` only by making plugin commands look like repo command wrappers, which preserves the current architectural split and duplicates plugin-pack responsibility in the command export path.

### Add `/ask` frontmatter to `skills/augur-core/commands/ask.md`

Rejected. It might make Gemini see a command wrapper, but it would not package the MCP, skills, and command surface as a native Gemini extension. It also keeps Codex and Claude behavior dependent on plugin-pack while Gemini follows a different path.

### Put Augur MCP config only in `~/.gemini/settings.json`

Rejected. Existing Gemini project config remains useful for project-level integration, but it does not provide a native extension bundle with namespaced commands and bundled skills.

## Implementation Prompt

Implement ADR-553 in small verified commits. Use test-driven development for each component: profile, formatter, assembler registration, sync adapter, and documentation/dashboard metadata. Do not add a centralized command registry. Do not remove existing `.gemini/skills/` generated wrappers. Verify with targeted pytest runs and an end-to-end `plugin_assembler.py --target gemini` assembly command before marking the ADR implemented.
