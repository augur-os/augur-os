Augur now has **post-spec SDLC autonomy** (ADR-810, rule 37, shipped to origin/main 2026-06-09, commit 9705f355b). Once the user approves a spec, the agent autonomously runs plan → code → test → `aug dev build` → browser-verify → ff-merge+push → memory, with the **approved spec as the authorization boundary**. Never: force-push/history-rewrite. Always-confirm: raw `rm -rf`/hard-delete (but `git rm` is fine), external publish/deploy/send. Outside grant: vault writes, secrets. Merges follow a no-loss stash→resolve→unstash→inspect→commit protocol. **Amended 2026-06-11 (commit a3822b15e, user-directed): merge/push is YOURS to finish** — at cycle end check for leftovers (another session's staged/uncommitted changes, a concurrent workstream's in-flight red tests, a held build/gate lock); if none, complete the ff-merge+push yourself instead of leaving publishing to the user; if leftovers exist, commit your own work by pathspec, leave the leftovers untouched, and surface what blocked the push.

**`aug dev build`** = the agent-callable dashboard build/restart (shared engine `src/lib/dev_build.py`; `/dev build` shares it; ADR-796's user surface unchanged). It does: preflight guard → gated scoped restart (`project-brain/capabilities/skills/daemon/scripts/scoped_restart.py` — stops only the instance's :port owner + its `dashboard-`-prefixed MCP children, identified by env `AUGUR_MCP_CLIENT_ID` startswith `dashboard-` + cwd==project_root + own-tree exclusion; never `pgrep -f mcp`, never launchd unload) → start-dev.sh → poll → verify fresh MCP. Production `pnpm run build` is opt-in (`full_build=True`); default uses the safe turbopack restart (a production .next crash-loops next dev).

**CRITICAL precondition (learned the hard way — it stranded :3000):** `aug dev build` only restarts cleanly when the dashboard CAN start — i.e. the main checkout is on `main`, OR you're in a worktree (own port). If the **main checkout is on a feature branch**, `start-dev.sh` preflight fails (`main_checkout_branch` check) and exits silently, so a naive stop+start would strand :3000. The engine now has a `_preflight_ok` guard that refuses (without stopping) when preflight fails. **Do branch work in a worktree (rule 33), not the main checkout** — that's the root cause of the strand. Recovery if :3000 is down: reset the gate state.json to `stopped` (`<runtime_dir>/daemon/dashboard/main/state.json`), then `bash apps/dashboard/scripts/start-dev.sh` (the dashboard_monitor daemon also auto-heals). The root `CLAUDE.md` is a gitignored generated projection of `docs/agent-topics/agent-rules.md` — edit the source, not CLAUDE.md. See [[category-action-refactor-spec]] and [[project-worktree-dashboard-port-verification]].

**Third mode — `ok:false` is a FALSE negative, not an outage (port-registry vs actual-bind mismatch, seen 2026-06-09, main checkout):** `aug dev build` returned `{"ok": false, "rebuilt": true, "mcp_recycled": true, "port": 3002}` while the dashboard was **perfectly healthy on :3000** the whole time. Root cause: `resolve_target()` resolved this checkout's `instance.dashboard_port` as **3002**, but the live `next-server` (PID, dir=main `apps/dashboard`) was actually bound to **:3000** (it grabbed 3000 at its original start). So `_poll_ready` polled :3002 (connection refused) → `ready=False` → `ok=False`, AND each `start-dev.sh` respawn aborted with `⚠ Port 3000 is in use by an unknown process, using 3002` + `⨯ Another next dev server is already running. Run kill <pid>` (Next's `.next/dev/lock` guard). Nothing was down. **Lesson: when `aug dev build` reports `ok:false`, before assuming an outage, find the port the live server actually binds — `lsof -nP -iTCP -sTCP:LISTEN | rg ':300'` and `ps -p <pid> -o command` (look for `next-server`) — then `curl` THAT port.** If it 200s, the dashboard is fine and the live server already HMR-compiled your edits; just browser-verify on the real port (here :3000). No gate reset needed. (Avoid the rule-29 hook on diagnostics: it pattern-matches `next dev`/`turbopack`/`start-dev`/`rm -rf .next`/`kill` in the command string — phrase probes without those literals, e.g. `lsof`/`curl`/`ps`, and read `~/Library/Logs/Augur/dashboard.stderr.log`.) **Root cause + FIX (2026-06-09, on origin/main `ed18290d4`):** the `worktree_registry.yaml` had a stray row keyed to the **main repo path** with `dashboard_port: 3002`. `resolve_dashboard_instance` read that registry row's port even for `kind=="main"`, so main resolved to 3002 while the canonical server ran on 3000. The row was created by `worktree_registry.py register --from-hook`, whose path **defaults to `os.getcwd()`** — a Claude Code session hook firing in the *main* checkout (no `CLAUDE_WORKTREE_PATH`) registered main as a worktree and `allocate_worktree_port` gave it 3002 (3000 reserved; `DASHBOARD_PORT_RANGE=(3001,3010)`). Two-layer fix: (1) `dashboard_instance.resolve_dashboard_instance` — the **main** instance's ports are now canonical (`.augur-worktree.yaml` marker or DEFAULT), never a registry row; (2) `worktree_registry.cmd_register` refuses the main working tree via new `is_main_working_tree()` (git `--absolute-git-dir` == `--git-common-dir` ⇒ main, not a linked worktree). Regression tests: `test_main_checkout_ignores_stray_registry_port_entry`, `test_register_refuses_main_working_tree`, `test_is_main_working_tree_distinguishes_main_from_linked_worktree`. To clean a pre-fix polluted registry: `python3 scripts/worktree_registry.py unregister --path <main-repo>`.

**Fourth mode — REAL port-drift strand (hung server → self-heal binds :3002 → singleton lock starves :3000; seen 2026-06-11, main checkout):** distinct from the third mode's false negative — here :3000 was genuinely dead. Chain: the main `next dev` (held :3000) **hung** (LISTEN but never answers; ~0 CPU) → the self-heal daemon restarted via `npm run dev`, whose `next dev` saw 3000 busy → **auto-incremented to :3002** (3001 = worktree) and went Ready → my `aug dev build` scoped-stop killed the hung :3000 pid (freeing the port) but every new `next dev` start then aborted with `⨯ Another next dev server is already running` — the :3002 instance owns Next 16's **dev-singleton lock** (keyed to the shared external `.next`), so `_poll_ready(:3000)` times out → `{"ok": false, "rebuilt": true}` twice, with start-dev.sh exiting silently (engine spawns it with stdout/stderr DEVNULL — read `~/Library/Logs/Augur/dashboard.stderr.log` instead). **Why `aug dev build` couldn't self-recover: `scoped_restart.stop_instance` only killed `pids_on_port(instance.dashboard_port)` (=3000), so a port-drifted instance was invisible to it. FIXED same day (origin/main `32b3b82c5`):** new `instance_dev_server_pids()` matches dev-server command markers (`DEV_SERVER_MARKERS`) whose **cwd is inside the instance's checkout** (own-tree and unknown-cwd excluded; worktrees scoped out by their own project_root), and `stop_instance` reaps those groups alongside the port pids, reporting `stopped_drifted_pids`. Verified live: a real zombie wrapper chain was reaped while the :3001 worktree chain survived; regression tests in `test_scoped_restart.py`. Side observation: the engine's `_start_server` and the daemon's self-heal can still race after a stop — both start, the singleton-lock loser becomes a zombie wrapper chain, but those now self-clean on the next scoped stop. Manual recovery (pre-fix strands): `request_gate` (action=restart, instance=main) → `scoped_restart.kill_process_group(<respawn-chain root pid>)` → `release_gate_stopped` → rerun `aug dev build` → ok:true on :3000. Diagnose drift fast: `lsof -nP -iTCP -sTCP:LISTEN | grep 300` + `ps -axo pid,ppid,etime,command | grep next` — a `next-server` rooted at `npm run dev` (ppid 1) on a non-canonical port is the daemon's drifted respawn.

**Second strand mode (worktree cold-start race, seen 2026-06-09 on :3001):** running `aug dev build` against a worktree whose dashboard is **not already running** (`.next` empty / nothing on its port) self-strands the gate. Mechanism: `_stop_instance` (scoped restart) flips the worktree gate to `starting`; then `_start_server`→`start-dev.sh`'s own build-lock sees `starting` and **denies itself** (`gate_denied: dashboard is starting, owned by agent:aug-dev-build`), so `next dev` never launches and `_poll_ready` times out → returns `{"ok": false, "rebuilt": true}` with the gate stuck in `starting`. The default path assumes a *live* dashboard (turbopack recompile) — it does not cold-start a down one cleanly. Diagnose: `dashboard_lifecycle.py state` shows `state=starting owner=agent:aug-dev-build`; the stuck state file is the **worktree-scoped** one `<runtime_dir>/daemon/dashboard/worktrees/<worktree-name>/state.json` (NOT `…/main/…`) — it's the only file containing `agent:aug-dev-build`. Recover: reset that file to `stopped`, then relaunch via the engine seam `python3 -c "from src.lib.dev_build import resolve_target, _start_server; _start_server(resolve_target())"` (or `bash apps/dashboard/scripts/start-dev.sh` from `apps/dashboard`). Do **not** re-run `aug dev build` to recover — its scoped-stop re-triggers the same race. The daemon then self-heals the gate to `healthy` on first 200. **Fixed 2026-06-09 (commit 663f9ad2f, on origin/main):** `scoped_restart.stop_instance` now calls `dashboard_lifecycle.mark_stopped()` (via the `release_gate_stopped` seam) after the kills, so a completed scoped stop leaves the gate `stopped` (not `starting`); the nested build-lock `start` is then granted (`stopped→compiling→healthy`) instead of denied. Verified: `aug dev build` against the live worktree dashboard returns ok:true with no `gate_denied` in the lifecycle trace. The manual gate-reset recovery above remains the fallback for pre-fix strands or unrelated stuck states. `mark_stopped` is a lock-protected lifecycle primitive (peer of `record_crash`/`record_healthy_poll`); regression tests in `test_dashboard_lifecycle.py` (gate handoff) and `test_scoped_restart.py` (release on stop, incl. cold no-process path; dry-run does not release).

**EnterWorktree create-side FIXED (2026-06-09, origin/main `fc6ad96a3` + stdio fix `2a93c78e2`):** EnterWorktree now works. The harness `WorktreeCreate` hook contract is *the hook creates the worktree and echoes its path to stdout* (the harness chdir's into that path; the requested name arrives via **stdin** `{"name": ...}`, not env). Augur's old hook only registered + leaked `worktree_registry.py`'s pretty-printed JSON (trailing line `}`), so the harness chdir'd to `}` (`ENOENT chdir … -> '}'`). Fix: (1) `runPythonScript` in `scripts/hooks/run-hook.mjs` drops child stdout (`stdio:["ignore","ignore","inherit"]`) so hook-driven Python never pollutes the hook's protocol stdout; (2) new `scripts/worktree_create.py` provisions a full Augur worktree (sibling `augur-<name>` + allocated ports + `.augur-worktree.yaml`, reusing `agent_launch` helpers) and the `worktree-create` handler echoes ONLY that path. `settings.json` `WorktreeCreate` → single `worktree-create` hook (timeout 60). Verified E2E: created + switched into `augur-ew-fix-verify`. **Remove-side caveat (OPEN follow-up):** `ExitWorktree(action:"remove")` does NOT delete the sibling `augur-*` worktree (only `.claude/worktrees/` ones) and `worktree-unregister` only unregisters — exiting leaves the dir + branch + registry entry. Clean up: `git worktree remove --force <path>` + `git branch -D <name>` + `python3 scripts/worktree_registry.py unregister --path <path>`.

Owner-aware (`active_ai_processes_for_path` covers every client) + refuses unmerged (no-loss). settings.json WorktreeRemove → `worktree-remove` (timeout 60); run-hook routes both `worktree-remove`/`worktree-unregister` to it.
