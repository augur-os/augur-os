# Adaptive loop maintenance surfaces

## Compiled truth

### Current Thesis

The adaptive loop system is best understood as a set of owner surfaces: each loop owns a quality domain, exposes action prompts, and reports findings without pretending all checks are complete.

### What This Page Knows

Loop skill pages describe consolidated owners for documentation, hub coverage, memory, observability, ops, quality, and repo hygiene. Action overviews add concrete scanner surfaces for command help, frontmatter, markdown quality, and instruction audits. The shared concept is a decentralized maintenance map: each loop owns a domain, reports findings, and evolves coverage when structural checks are green but semantic confidence is still incomplete.

### Key Dimensions

- action prompt overview pages as operator surfaces
- domain-specific loop ownership
- evolution gaps when green checks do not cover enough behavior
- quality gates for markdown, frontmatter, and command help

### Recent Shifts

- Loop pages are increasingly consolidated owner surfaces rather than scattered command wrappers.
- Quality gates are moving from structural pass/fail checks toward semantic and user-visible maintenance findings.

### Open Tensions

- Centralized loop inventories can help triage but conflict with the decentralized skill ownership principle if they become canonical.
- Too many green loops without evolution gaps can hide coverage weakness.

### How to Use This

Use this concept to route maintenance findings to the correct loop owner and decide whether a green result still needs evolution work.

### Open Questions

- How should loop surfaces report source coverage without adding central config debt?
- Which loops still lack semantic checks beyond markdown structure?
